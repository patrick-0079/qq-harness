# 2026-10-26 设计与缺陷检查报告

## 范围与结论

只检查、修改 `qq-harness`。旧 `source` 仅作参考，未修改。检查范围包括宿主装配、Cordis 生命周期、通用调度与扩展点、接入/发送/工具/模型链路、记忆、提醒、SnowLuma 进程托管、容器、兼容层与客户端依赖。

总体分层合理：内核保持业务无关，服务可替换，前后端贡献有归属，SQLite 与兼容层均有独立边界。主要缺陷集中在依赖声明不完整、异步生命周期边界和配置开关未覆盖后台行为。下面 12 类问题已修复并增加行为回归用例；没有把检查结果表述为“系统不存在其他 bug”。

结构图见 [系统结构与消息流](system-map.md)，每个插件的依赖见 [生成清单与图](plugin-dependencies.md)。清单包含 38 个插件目录和 1 个独立后装示例，并区分后端服务依赖、客户端插件依赖与可选调用。

## 仍建议改进的设计

以下是本轮识别但未混入修复的独立设计事项：

1. **后台记忆的模型并发不受 Runs 全局槽位约束。** [memoryBackground.process](../plugins/agent-memory/src/background.ts) 直接调用 model.complete，仅以 chatKey 防同会话重复。大量会话同时达到 30 条消息阈值时，后台提炼可并发超出前台配置；这部分调用也没有前台运行的同等 usage 档案。建议引入独立的后台运行模式或共享模型请求限流与记账服务，并增加多会话压力测试。
2. **消息去重路径读取全部会话历史。** [conversation.ingest](../plugins/conversation/src/index.ts) 在有限 seen 缓存未命中时调用 storage.messages(chatKey).some；新消息绝大多数不在 seen，历史增长会增加每条消息的查询、反序列化与内存成本。建议给 StorageService 增加按 chatKey/messageId/self 的存在性查询，SQLite 利用现有唯一键查询，文件仓储维护对应索引，并同步存储替代契约测试。

此外，Node 插件仍是受信任代码；同进程超时只能撤销提交资格，不能强制停止死循环或任意插件自行创建的资源。现有分层没有承诺恶意插件沙箱。消息发送也不能承诺 exactly-once：网络中断时可能出现“协议端已收到但本地未收到确认”，需要业务幂等或人工核对策略。

## 文档维护

`npm run docs:dependencies` 仅读取插件定义和源码，不调用 setup/start、不创建文档占位数据目录、不连接服务。`npm run check:dependencies` 校验生成文档是否与当前定义一致。服务提供/调用关系采用静态提取，不声称穷尽动态社区扩展或所有条件分支；完整依赖表同时保留实际 requires 声明。
